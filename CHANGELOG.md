# Changelog

All notable changes to this project will be documented in this file.

## [Unreleased]

### Fixed
- A short work order prints on one letter page. Large sections can split, spec fields print in rows of three, and pages after the first of a work order repeat the work order number and customer. The due time falls back to the time on the work order when the order has none, and that time drives overdue and due soon. OVERDUE prints only for an active work order. Order date, history, file, created, and updated times use the shop timezone. The due-date zone label is the offset for that due date, such as EST or EDT. Special instructions on the work order page fall back to the order notes. Moving a work order names the work order number
- Renaming a department updates every live copy of that name in the same transaction: `users.department`, `work_orders.department`, `work_orders.next_department`, `services.department_name`, `departments.next_department`, `barcode_locations.department_name`, and `barcode_locations.location` when the location is still named the department. A location an admin renamed is left as saved. Production history, barcode event from/to/location, activity detail, and notification text stay as written. One `department.updated` row records how many rows changed in each table. `work_orders.assigned_department_id` already follows the department row
- Department names are unique ignoring case. Creating or renaming onto a name that differs only by case returns HTTP 409. `work_orders.department` and `work_orders.next_department` follow a rename when the stored text matches after trimming and ignoring case. Users, services, department routes, and scan locations still match the previous name exactly, so a different casing of those is not rewritten
- Init seeds default departments once. `system_settings.departments_seeded` records the names already considered. A later init does not recreate a department that was renamed or removed. A database that already has departments records the current seed names and does not insert the missing ones. A seed name added after that flag exists is inserted once. That lookup ignores case, so a name that differs only by case does not fail init on the unique index
- Quality, Dispatch, and Complete cannot be renamed, including a case-only change. `PUT /api/departments/:id` returns HTTP 400 and names that system department. The complete queue and the Quality and Dispatch scan stages still use those names
- Admin Board tabs, the queue summary, and empty-queue alerts follow departments with `show_on_board` set, in `sort_order`. Reprographics and Admin start off that list, so an upgraded database keeps the previous tabs. The flag is filled in only when the column is added. New departments default to shown, and Departments has a Show on board toggle. A department with active work still appears, including Manufacturing and Assembly. An inactive department is omitted when it has no active work. Empty-queue alerts skip Complete. A renamed department keeps its tab, its empty-queue alert, and its entry-queue stat card. Those cards are the active departments whose `sort_order` is 1 through 5
- `PUT /api/departments/:id` leaves description, color, icon, sort order, active, and show on board unchanged when those fields are omitted or null. An empty string still clears a text field. The name is still required
- Saving a work order stores `departments.name` when the submitted department matches one, ignoring case and surrounding spaces. A name that is not in the table is stored trimmed
- A header-scan error or warning stays up when a later success comes back. A milder result waits, and a more severe result replaces the one on screen without showing that one again. Pending errors and warnings are capped at five, and pending successes collapse to the latest one. A toast stays for 4 seconds when it is alone and yields after about 1.5 seconds when others are waiting. Closing the snackbar, or letting it close on its own, returns focus to the scan box only when that box had focus
- The restricted Admin Board no longer fails when `activity_log.detail` is not JSON
- The header scan box stays focused after a scan. `readOnly` is used while a scan is posting, and barcodes entered during that request are queued and posted in order. The box clears on Enter, and each result gets its own snackbar
- Recent Activity and pending approvals for a staff user with a department stay on work orders in that department. User and system events such as creating an operator are omitted. An admin with no department, and an admin who chooses All departments, still see the full lists
- A login whose department is Complete defaults to work orders completed this month, newest first, instead of an empty active list. The board chip reads `Showing: Complete · completed this month`
- Assigning a department that is not in the departments table, including legacy board names such as Manufacturing and Assembly, returns the valid department names in the error
- The staff drawer lists Scan (`/scan`) for admin and operator, directly after Create Order. Customers still do not see it
- Scan locations follow department names. Quality Control maps to Quality and Shipping maps to Dispatch, so a scan moves the work order and the Admin Board shows the new department. Finishing is no longer offered as a default location. Init updates an already-seeded database once and leaves locations an admin has edited
- Heavy mixed load no longer stalls scans. The server raises libuv's thread pool to 32 when unset, and barcode inserts, stage updates, and notification writes wait on the same writer queue as other transactions
- Creating customers with the same display name at the same time no longer fails the unique username constraint. The name is reserved inside the create transaction
- Admin writes no longer share one SQLite transaction. Concurrent user, settings, and notification updates each take a queued connection, and the last-admin check runs inside that transaction
- Creating a customer from the older customers API records activity and uses the same username rules as the Users page. Customer lookup omits deactivated accounts
- Passwords longer than 72 bytes are rejected. Init does not restore a barcode location an admin deleted
- Staff cannot save a work order number that Code 128 cannot draw. `external_id` must be 1 to 80 printable ASCII characters, or be left blank. A value already stored that cannot be encoded prints "barcode unavailable" instead of failing that sheet or the rest of the order
- A barcode scan that moves a department writes the scan, the department change, production history, and the activity row in one transaction

### Added
- Branded work order page and printable production ticket. The print view at `/work-orders/:id/print` and `/orders/:id/print` uses the Accent Imaging logo on a navy header, the work order number, and the existing Code 128 barcode on white with a quiet zone and the number under the bars. Order date, due date and time, and delivery method sit under the header. The due line uses the short zone name for that due date, such as EST or EDT when `DELIVERY_TIMEZONE` is `America/New_York`. Sections use navy headers and an orange accent: Customer, Bill To / Ship To / Delivery, job details with wrapping line summaries, originals and files, special instructions, proof, and payment. A sign-off block has Prepress, Production, Finishing, Quality, and Dispatch with initials and date lines. The footer prints the letterhead from system settings when those values are present, the print timestamp, and a page number. Letter margins are 0.45in. Each work order on an order print starts on its own page. Later pages of that work order repeat its number and customer. Rush prints when priority is Rush. Overdue prints when an active work order's due time has passed. The time comes from the order, or from the work order due date when the order has none. The work order page uses the same groups, department colors from the departments table, and the existing Print, Move to…, and Edit actions. Routing history and activity still mark a manual move
- `backend/scripts/verify-phase12.js` for the print timing fields, the due-date zone label, rush, overdue including a work order with no order due time, and the barcode still decoding
- A manager role. A manager can do everything an operator can do, and can move any work order without scanning. A manager is not assigned a department. A manager is not an administrator: Users, Services, System Settings, Activity Log, Barcode Settings, Departments, customer administration, and archive approval decisions stay admin-only. The manager board shows every department, the same as an admin with no department, and does not show a department chip. Operators with a department still cannot widen the board. An admin with a department still can. `POST /api/workorders/:id/move` accepts `{ department, note? }` for admin and manager. The department must be active. The current department returns HTTP 409. The move updates the department, next department, production history, and stage the same way a scan does, and writes `work_order.moved` with `manual: true`, the signed-in user, and the note. The stage comes from the active barcode location for that department, and a blank stage stays blank. The built-in map is used only when that table has no active row for the department. Complete marks the work order completed. A manager can move a work order in any department. The Admin Board and the work order page show Move to… for admin and manager. The Users page does not ask for a department on a manager. Creating a manager, or changing an account to a manager, stores no department. Init clears a department already stored on a manager, and a later init leaves those rows alone. A successful move shows a snackbar and refreshes the board. History and activity mark the move Manual and show the note. The current schema does not CHECK `users.role`. Init rebuilds `users` inside a transaction only when an older database has a CHECK that omits manager. That rebuild rewrites only the role CHECK in the original CREATE TABLE statement, so the username collation, other CHECK constraints, indexes, foreign keys, triggers, and rows stay. Running init again does not rebuild
- `backend/scripts/verify-phase10.js` for the role migration, manager permissions, the manual move, and customer isolation
- A department on each staff login. Null means every department. The Admin Board then shows only that department's active work orders, and a scan uses the barcode location with the same name. Operators cannot widen the board or their scan list. An admin with a department can choose All departments. Staff get a scan box in the top bar. `users.department` is added by `schema.sql` and by an idempotent `init_db.js` pass
- `backend/scripts/verify-phase8.js` for the department migration, user department updates, board restriction, department scans, and customer isolation
- `backend/scripts/verify-phase9.js` for the department rename cascade, case-only name conflicts, the one-time department seed, system departments, and a restricted board with a non-JSON activity detail
- Case-insensitive uniqueness for department names (`idx_departments_name_nocase`), added by an idempotent `init_db.js` pass that skips the index and warns when an older database already has case-only duplicates
- Small Format product, paper, finished size, sides/color, binding, folding, finishing, and proof lists. Product is required. Finishing accepts more than one option. Proof defaults to None, or to the digital proof when None is turned off, and prints with the other line fields. Init fills an empty or untouched list and, when an admin has edited one, only adds missing options
- Per-service line item fields. `service_fields` stores the label, type, options, required flag, and sort order for each service. `order_line_items.field_values` stores the answers as JSON. The customer order form shows a section for each selected service. The server checks required fields and select values against the active definitions. Admins edit those lists on the Services page. A deactivated option still displays on older orders. Init adds missing seed rows and does not overwrite an admin's edits
- Signs & Graphics product fields for flatbed, CNC router, and the rest of the widened product line. Mount and laminate are options on that service, not a separate service. Older Yes/No mount and laminate values still display
- Required payment method on new orders: Accent Account, Cash, Check, AMEX, Master Card, Visa, or Discover. Only the method label is stored. Older orders display `Not specified`
- Optional Bill To person and company address, shown on the order and the print sheet when present. Customers can prefill from their own earlier Bill To entries
- Return `To Me` or `See ShipTo`. Selecting Ship To (3rd Party) defaults return to See ShipTo. An omitted delivery method then follows the first recipient's Via
- `backend/scripts/verify-phase5.js` for field validation, the admin editor, payment, Bill To, legacy rows, and concurrent saves
- The order form starts with no payment method selected. Service field edits record a short added, removed, and changed summary. Ship To Via options must map to Will Call, Accent Truck, or UPS, and an unmapped Via names itself in the error. Field keys cannot be constructor, prototype, or __proto__
- Line-item finishing on the order form (None, Grommets, Easel, Cut/Trim, Velcro, Print Hanger, Framing, See Notes). The value is stored on the line and printed. None is stored blank and prints as `Finishing: None`
- Required project name on order create. Orders that already have no project name still load and print
- A line item for each selected service. Archive File Request can instead be described in Notes. Ship To (3rd Party) can instead be described in Ship To. An empty service returns HTTP 400 naming that service
- Required originals source: files attached, archived files at Accent Imaging, an inbound vehicle pickup, or hardcopy or digital media. Files attached shows the upload area and requires a file. The pickup is not a delivery method. Older orders display `Not specified`
- Company address (Addr 1, Addr 2, City, State, Zip) on the customer profile and snapshotted onto the order. Addr 1, City, State, and Zip are required on the order form. Admins edit the profile on Users and Customers. Older orders leave the address blank
- `orders.originals_source` and address columns on `orders` and `users`, added by `schema.sql` and by an idempotent `init_db.js` pass
- Optional UPS account number on orders when the delivery method is UPS. It is trimmed, limited to 30 characters, and allows letters, digits, spaces, and dashes. It is not required. The customer order form, order detail, work order detail, the work order edit form, the print sheet, and the deliveries CSV include it when it is set
- `orders.ups_account_number`, added by `schema.sql` and by an idempotent `init_db.js` pass
- Separate Will Call hours (`WILL_CALL_WINDOW_START` / `WILL_CALL_WINDOW_END`, default 8:00 AM–5:00 PM) and delivery hours (`DELIVERY_WINDOW_START` / `DELIVERY_WINDOW_END`, default 9:00 AM–4:00 PM), shown on the order form, print sheet, delivery rules, and System Settings

### Changed
- Customer Pickup, FedEx, and Common Carrier are no longer selectable or accepted on new orders. Will Call is the pickup method. UPS and Accent Truck (shop delivery) stay. Init deactivates retired method rows when they already exist and does not delete them or rewrite stored labels. Customer Pickup on an existing order keeps that label and uses Will Call hours
- Same-day cutoffs stay 15:00 for will call and 14:00 for other methods. Both are inside the new hours, so a blank delivery due time is still the cutoff. Overdue and due-soon still use the stored due timestamp
- The printable work order uses the letterhead stored in system settings
- Operators can open Search Orders and the Reports menu. Services, Users, System Settings, Activity Log, and Barcode Settings stay admin-only
- A barcode scan uses `barcode_locations` when that table has any row. An empty table still uses `BARCODE_LOCATION_STAGES` and a department-name match
- Admin and operator land on the Admin Board instead of the earlier home dashboard. Customers still open the order form
- The staff sidebar follows the admin mockup. Operators see Admin Board, Create Order, Search Orders, Reports, and Notifications
- A barcode scan whose location names a department moves that work order. Scanning into Complete also marks it completed. Other locations keep the existing production-stage map
- Editing a work order's department updates `next_department` from the department route when that department exists
- The due-soon window defaults to 1 hour. `DUE_SOON_HOURS` defaults to 1, and `DELIVERY_DUE_SOON_MINUTES` defaults to 60. When the minutes setting is unset, notifications use the delivery-list window
- The Reports navigation item opens the reports page for admin and operator. Customers are still blocked from that route and from the report APIs
- `init_db.js` creates the notification tables when they are missing, including on a database created before this change
- Removed the placeholder `POST /api/barcode` and `GET /api/delivery/rules` handlers from `server.js`
- `GET /api/delivery` now returns `{ deliveries, total, limit, offset, evaluated_at }` with work order fields and timing flags. Customers still only see their own work orders
- Delivery due times follow `backend/deliveryRules.js`. Cutoff times, timezone, and the due-soon window are environment settings
- Operators can select an existing customer on the work order form. New customers must still be created by an administrator
- A password supplied to `POST /api/customers` must be at least 8 characters
- `INIT_ADMIN_PASSWORD` is no longer optional with a hardcoded fallback. When it is unset, database init generates a random admin password and prints it once
- Seeded customer accounts no longer use published passwords
- Customer, department, work order, dashboard, and production board routes enforce roles. Customers only receive their own work orders, and their home page does not call the staff dashboard or production board
- Work order statuses are `open`, `in-progress`, `completed`, and `on-hold`. `PUT /api/workorders/:id/stage` requires a numeric work order id and an existing numeric `stage_id`
- Duplicate department names return HTTP 409
- Extended work order schema with new fields for specifications, start date, production line, routing instructions, attachments, and notes (`database/schema.sql`)
- Added database migration logic to preserve existing work orders when adding new columns (`backend/init_db.js`)
- Added edit action to work order detail page
- Added "New Work Order" button on work order list page

### Fixed
- Simultaneous `POST /api/orders` calls no longer fail with `SQLITE_BUSY`. Order numbers stay unique, and a rolled-back create does not leave a gap
- A line item with no `service_id` on a multi-service order is rejected instead of being left off the work orders
- Customers can delete an uploaded file only before it is attached to a submitted order
- Customer work order detail shows production history as department, status, and timestamps. Internal fields such as `scanned_by` stay on the staff response
- `work_orders.external_id` gets a unique index when existing values are already unique. Init logs a warning and continues when duplicates are present
- Legacy work order status `complete` is normalized to `completed` on save and by an idempotent database init migration. Lists, detail, and the dashboard treat `complete` and `completed` as the same finished status
- `PUT /api/workorders/:id/priority` requires a positive integer id
- Database init no longer exits before departments, stages, and sample data are seeded, and it always exits after each independent seed step
- Sample production board and delivery rows reference real work order ids
- Removed the unused `addColumnIfMissing` helper
- API errors no longer include raw database messages
- Customer creation uses `datetime('now')` and no longer discards the generated password
- Corrected inconsistent frontend work order route paths
