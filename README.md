# Launchpad 3.0

Launchpad 3.0 — initial scaffold for a manufacturing/work-order web app.

Architecture:
- Frontend: React (separate `frontend/` folder)
- Backend: Node.js + Express (in `backend/` folder)
- Database: SQLite (schema in `database/`)
- Assets: static files in `assets/`
- Docs: project requirements and notes in `docs/`

Getting started (backend):

1. Change to `backend/` and install dependencies:

```bash
cd backend
npm install
```

2. Copy `.env.example` to `.env` and adjust values. Set `INIT_ADMIN_PASSWORD` before the first seed if you want a chosen admin password. If it is omitted, `init_db.js` generates a random password and prints it once. That value is not stored anywhere else.

3. Initialize the database:

```bash
node init_db.js
```

Seeding is idempotent. Creating the admin user, customer users, departments, production stages, sample orders, board rows, and deliveries are separate steps, so an existing admin user does not skip the rest of the seed. Sample board and delivery rows point at the seeded work orders by external id. Seeded customer users (`acme`, `whitebox`, `orion`) get random unknown passwords and cannot log in until an administrator resets the password from the Customers page or creates a new account. Passwords other than a newly generated admin password are never printed.

4. Start the backend:

```bash
npm start
```

Frontend:
- `frontend/` is a Vite + React app. From that folder, run `npm install` and `npm run dev`.
- Navigation follows the signed-in role. Customers see their own work orders and deliveries. The production board, barcode scan page, customer directory, and admin pages are hidden from roles that cannot use them.

Security notes:
- Passwords are stored with bcrypt. A successful login still accepts a legacy unsalted SHA-256 hash once, then replaces it with bcrypt.
- Sessions expire after `SESSION_TTL_HOURS` (default 8). `POST /api/auth/logout` clears the bearer session. Expired sessions are removed on use and by a periodic cleanup.
- `POST /api/auth/login` is limited to 10 attempts per 15 minutes for each IP and username. Set `TRUST_PROXY` (see `backend/.env.example`) when the API is behind a reverse proxy so that limit uses the client IP from `X-Forwarded-For`. Sign-in matches the username ignoring case, so a customer who registered with an email can type that email in any case.
- Customers can create an account from the sign-in page when `system_settings.customer_self_signup_enabled` is on (the default). `GET /api/auth/config` is public and returns that flag. The page hides Create an account when the flag is false. `POST /api/auth/register` accepts company, contact name, email, phone, password, and password confirmation. The email is stored as the username and is the sign-in name. The account is active immediately and the response is the same session payload as login, so the customer lands on the order form. The role is always `customer`. A role or department in the body is ignored. Address fields are optional and use the same rules as an admin-created customer. A duplicate email or username, ignoring case and surrounding spaces, returns HTTP 409, "An account with that email already exists". An apostrophe or plus in the username is allowed, including on admin create, admin update, and sign-in. An update that leaves the username unchanged does not re-check it. An administrator can still give two companies the same ordering email. Passwords follow the existing rule (at least 8 characters and at most 72 bytes) and are stored with bcrypt. A non-empty `website` field is a honeypot and is rejected without creating an account. Registration counts 5 successful registrations or honeypot hits per hour for each IP, 30 attempts per hour for each IP, and 200 attempts per hour overall (`REGISTER_RATE_IP_MAX`, `REGISTER_RATE_IP_ATTEMPT_MAX`, `REGISTER_RATE_GLOBAL_MAX`, `REGISTER_RATE_WINDOW_MS`). Validation and duplicate errors do not use the success count. The success cap reserves a slot before the account is created, so parallel sign-ups from one IP cannot pass it, and releases that slot unless the account is created or the honeypot trips. The counters are in memory and reset when the process restarts. Turning the setting off on System Settings returns HTTP 403 from the register endpoint. Existing customers can still sign in. The write is activity `customer.self_registered`. Staff also get an in-app notification, "New customer account: <company>", unless that event is disabled on the Notifications page. No email is sent. `node scripts/verify-phase11.js` checks this path, customer isolation, and an upgrade that does not turn the switch back on.
- `POST /api/barcode` is limited per signed-in user (`BARCODE_RATE_LIMIT_MAX` scans per `BARCODE_RATE_LIMIT_WINDOW_SECONDS`, default 60 per 60 seconds). Restart the server after changing those values.
- `POST /api/customers` is admin-only. Omit `password` to receive a one-time random password in the create response. A supplied password must be at least 8 characters, is stored, and is not echoed back. Omit `username` and the display name is turned into one. A generated name already in use, in any case, gets a numeric suffix. An explicit username that is already in use returns HTTP 409. That check runs inside the create transaction, so overlapping creates do not collide. A leftover unique constraint on create or user update returns HTTP 409.
- `PUT /api/customers/:id/password` is admin-only and only updates users whose role is `customer`. Omit `password` to generate one. The new password is returned once as `{ id, username, password }` and is not written to the server log. The customer's active sessions are cleared, so they must sign in again. The Customers page lets an admin set or generate that password and copy it.
- `GET /api/customers/lookup` is available to admin, manager, and operator and returns only `id`, `username`, and `display_name`. Managers and operators use it to pick an existing customer on a work order. Creating a customer from the directory stays admin-only. A customer can also register from the sign-in page, which creates the same kind of customer user.
- Customer create, company address, and password reset stay admin-only. `GET /api/customers` and `PUT /api/customers/:id/texting` are available to admin and manager. Department create/update/delete require the admin role. Work order create, update, stage, and priority changes require admin, manager, or operator. Customers can read only their own work orders. The dashboard and production board are limited to admin, manager, and operator; the customer home page shows only that customer's orders.
- Report endpoints require admin, manager, or operator. Notification endpoints require a signed-in user and then limit rows by role. Admin and manager see every notification, the same as an operator.
- Work order status values are `open`, `in-progress`, `completed`, and `on-hold`. A legacy `complete` value is rewritten to `completed` when the database is initialized and when a work order is saved. Delivery status values are `pending`, `scheduled`, `out-for-delivery`, and `complete`.

Barcode scans:
- `POST /api/barcode` (admin, manager, or operator) stores `scanned_value`, the resolved `work_order_id`, `operator_id` from the session, `location`, and `event_time` on `barcode_events`.
- The scanned value matches `work_orders.external_id` exactly first (for example `WO-1001`). If that misses and the value is a positive integer, it matches `work_orders.id`. Unknown values return 404. Missing or invalid input returns 400.
- `GET /api/barcode/events` (admin, manager, or operator) filters by `work_order_id`, `operator` (user id or username), and `from` / `to`, with `limit` (default 50, max 200) and `offset`.
- `GET /api/workorders/:id/events` returns that order's scans. Customers only receive events for their own work orders.
- Scan locations live in `barcode_locations`. Admins edit them on Barcode Settings. A location can name a department, a production stage, or both. Once any row exists, only an active row moves the department or advances the stage. An empty table keeps the older rules: `BARCODE_LOCATION_STAGES` (unset means Quality advances the Quality Control stage, and Dispatch advances the Shipping stage) plus a match against a department name. Finishing is not a default scan location. Init seeds one active location per active department, and stores those stages on Quality and Dispatch. A later init does not overwrite a saved row and does not restore a location an admin deleted. A database that already has the older stage-only Quality Control, Shipping, and Finishing rows is updated once. Quality Control maps to the Quality department and Shipping maps to Dispatch. When a department-named row already exists, the old row is turned off so the scan list shows one Quality and one Dispatch. Scanning the old name still moves the work order. Finishing is turned off. A row an admin already edited (a department was set, or the stage no longer matches that original seed) is left alone. Scanning into Complete also sets the work order status to `completed`. `POST /api/barcode/dry-run` (admin) shows how a typed value would resolve and writes nothing. `barcode_events.stage_id` records the stage that was applied. The scan response includes `department_moved` and `department_move_reason` (`moved`, `same_department`, `stage_only`, `unknown_location`, `no_location`, or `department_not_found`).
- Operators use the Scan page (`/scan`). The location list shows the department each station moves the work order to. A scan that does not change the department shows a warning. The barcode field accepts keyboard-wedge input and submits on Enter. Work order detail shows the scan history tab. The Admin Board reloads active work orders and scan activity when the page is opened again or the window regains focus. Staff also have a scan box in the center of the top bar. Enter submits it, the same way a USB scanner does, and clears the box immediately. A barcode entered while a scan is still posting is queued and posted next, in order, and each result has its own snackbar. An error or warning stays on screen when a later success comes back. A milder result waits behind it, and a more severe result takes the screen without showing the replaced one again. Pending errors and warnings are capped at five, and pending successes collapse to the latest one. A toast stays for 4 seconds when nothing is waiting and yields after about 1.5 seconds when another result is queued. Closing the snackbar, or letting it close on its own, returns focus to the scan box only when that box had focus. The box stays focused after a scan so the next wedge scan is not dropped. Alt+S or a click focuses that box. It does not take focus from another field someone is typing in, except after a scan and when the Admin Board opens.
- A staff user with a department set scans at the barcode location whose name equals that department. A different location in the request does not replace it. Users with no department still choose a location on the Scan page. Scan Activity on the board follows the board scope. `GET /api/barcode/events` for an operator with a department includes only scans whose location, from department, or to department is that department. Operators cannot remove that limit on the events list. Admins and managers read the full event list. A manager is not limited to one scan location.

Deliveries:
- `GET /api/delivery` lists deliveries with work order and customer fields, plus `overdue`, `due_today`, `due_soon`, and `timing`. Customers only see deliveries for their own work orders. The response is `{ deliveries, total, limit, offset, evaluated_at }`.
- `POST /api/delivery` and `PUT /api/delivery/:id` are admin or operator. A delivery stores `will_call`, `due_time`, `carrier`, and `status`. Several deliveries may exist for one work order. Updating a delivery does not change its work order.
- Leave `due_time` blank on create, or send null on update, to calculate it. Will-call uses `WILL_CALL_CUTOFF` (default `15:00`). Other deliveries use `CARRIER_CUTOFF` (default `14:00`). If the order is ready before the cutoff on a Monday–Friday, it is due that day at the cutoff; at the cutoff or later, or on a weekend, it is due the next business day at the cutoff. Holidays are not skipped. Times are wall-clock in `DELIVERY_TIMEZONE`. When that variable is unset the code default is `UTC`; `backend/.env.example` sets `America/New_York` for the shop. `DUE_SOON_HOURS` (default 1) marks a non-complete delivery due soon. Completed deliveries are not marked overdue. Overdue and due-soon compare the stored due timestamp with now, including older orders whose time sits outside the current request window.
- Will Call hours are `WILL_CALL_WINDOW_START` through `WILL_CALL_WINDOW_END` (default 8:00 AM–5:00 PM). Delivery hours for every other method are `DELIVERY_WINDOW_START` through `DELIVERY_WINDOW_END` (default 9:00 AM–4:00 PM). The same-day cutoffs stay 3:00 PM for will call and 2:00 PM for other methods because both fall inside those hours. A blank due time is still the cutoff, not the end of the window.
- `GET /api/delivery/rules` returns those rules and a computed suggestion for an order ready now.
- The Delivery page highlights overdue and due-today rows and shows a will-call badge. Customers can open it read-only.

Customer orders:
- An order groups one or more work orders. The order number is `YYYYMMDD-NNN` (for example `20260609-041`). The sequence resets each day in `DELIVERY_TIMEZONE` and is stored in `order_sequences`. Creates are serialized in process and retried if SQLite reports the database is busy, so overlapping requests keep unique numbers. A number is used only after the transaction commits.
- `POST /api/orders` (customer, admin, or operator) creates the order, its line items, and one work order per selected service in a single transaction. Work order numbers add `-A`, `-B`, `-C`, and so on, in service sort order. Customers can read only their own orders (`GET /api/orders`, `GET /api/orders/:id`). Staff creating an order must send `customer_id` for an existing customer. Customers cannot set production fields such as status, priority, assignment, or approval.
- Required fields are company, contact name, phone, email, company address (Addr 1, City, State, and Zip; Addr 2 is optional), project name, originals source, payment method, due date, due time, and at least one service. Delivery method is required unless Return is See ShipTo and a Ship To line names a via. Due date must be a Monday–Friday, not before today in the delivery timezone. Due time must be a slot inside the window for the chosen method, in `DELIVERY_SLOT_MINUTES` (default 15). Will Call is 8:00 AM–5:00 PM. Accent Truck, UPS, and any other active method are 9:00 AM–4:00 PM. The same wall-clock normalization as other deliveries stores that due time. A time outside that window is HTTP 400. Text is trimmed, length-limited, and rejected when it contains control characters. Addr 2, notes, and Ship To may include newlines. State is letters, spaces, periods, apostrophes, or hyphens. Zip is 2 to 20 letters, digits, spaces, or hyphens, so a value such as `=1+1` is rejected before it can reach a CSV.
- A delivery row is created for the order. `will_call` follows the delivery method. Selectable methods are Will Call, UPS, and Accent Truck (the shop delivery). UPS may include an optional `ups_account_number`: trimmed, at most 30 characters, letters, digits, spaces, and dashes. It is stored only for UPS, omitted from activity text, and returned only on that customer's order. Customer Pickup, FedEx, and Common Carrier are rejected on new orders with HTTP 400. Init inserts a missing active name and, when an older database already has a retired name, marks that row inactive. It does not delete the row or rewrite an existing order. Customer Pickup keeps its stored label and uses Will Call hours. FedEx and Common Carrier keep their labels and use delivery hours. The seeded WO-1001 delivery still records carrier FedEx so that older label stays visible.
- Services are seeded to match the order form: Large Format, Small Format, Signs & Graphics, Scanning, Planroom, Archive File Request, and Ship To (3rd Party). Each service opens a work order in a department. Archive File Request is marked pending approval for a later approvals screen. New departments (Large Format, Planroom, Archive File, Quality, Dispatch, Complete) are added on a fresh database. Init records those seed names in `system_settings.departments_seeded`. A later init does not insert a name already in that list, so renaming or removing a default does not bring the old row back. A database that already has departments gets the flag and does not gain a second copy of a renamed default. A seed name added after the flag exists is inserted once. Production departments route to Quality, then Dispatch, Delivery, and Complete. That route is filled in only when a department row has never been edited.
- Line items store description, size, quantity, media, color, binding/finish, finishing, mount, and laminate, plus `field_values` JSON for the service-specific answers. Each service has its own fields in `service_fields` (text, select, multiselect, number, checkbox, or textarea). Small Format Product is a required dropdown. Paper Stock, Finished Size, Sides/Color, and Binding extend the older media, size, sides, and binding fields. Folding and Finishing are optional; Finishing is a multiselect. Proof is optional and defaults to None, or to the active digital proof when None is off. It is shown with the other service fields on the order and the print sheet. Init replaces a Small Format option list only when it is empty or still the original seed, and otherwise adds missing options without deleting or duplicating an admin's entries. The order form shows those fields only for the services the customer selected. Required fields and select values are checked on the server against the active definitions. A select value must match an active option exactly. A multiselect value is a list of active options, with no duplicates. Deactivating an option blocks new orders and still displays the stored value on older orders. Notes, the ship-to account number, address line 2, the scanning Index/Name File checkbox, and Small Format folding, finishing, and proof are optional. The other seeded fields are required when a line is submitted. Finishing on a line that does not send a finishing field is still one of None, Grommets, Easel, Cut/Trim, Velcro, Print Hanger, Framing, or See Notes. None and a blank value are stored as null and print as `Finishing: None`. Signs & Graphics stores Mount and Laminate as the option text. Anything other than `No` is also mirrored to the older Yes/No columns so existing reports keep a number. Older rows with no `field_values` keep Mount Yes/No. Mounting and lamination are not a separate service. Each selected service needs at least one line item. Archive File Request is also satisfied by notes that name the files to pull, and that service still opens a work order pending approval. Ship To (3rd Party) is also satisfied by a Ship To address. Those two do not need a line when that detail is present. Any other empty service returns HTTP 400, for example `Large Format is empty. Please add lines or deselect it.` A line item is linked to the work order for its service. With one selected service, an omitted service is assumed. When more than one service is selected, a line item without `service_id` is rejected. Work order detail shows the service fields, attached files, and routing (department, current status, next department). Customers see production history as department, status, and timestamps. Staff also see who recorded the step and the notes.
- Payment method is required on a new order: Accent Account, Cash, Check, AMEX, Master Card, Visa, or Discover. The order form starts on “Select payment method” so the choice is explicit. Only the label is stored. Card numbers are not collected. Orders created before the column existed have a null value and display as `Not specified`.
- Bill To is optional. Person name, phone, and email are optional. Phone must contain a digit when it is present, and email must be an email address. A company name alone does not require an address. If any address field is filled in, Addr 1, City, State, and Zip are required and use the same rules as the company address. The order detail and the print sheet show Bill To only when something was entered. `GET /api/orders/bill-tos` lists the signed-in customer's own previous Bill To entries. Staff must pass `customer_id` for an active customer. A customer query cannot read another customer's entries.
- Return is `To Me` unless the Ship To (3rd Party) service is selected, in which case an omitted return becomes `See ShipTo`. Sending `See ShipTo` without that service is HTTP 400. When return is See ShipTo and delivery method is omitted, the first ship-to line's Via chooses the method: Pickup at Accent becomes Will Call, Accent Truck stays Accent Truck, and Ground, 1 day, or 2 day become UPS. Any other active Via is HTTP 400 and names that value. An explicit delivery method is still accepted. Saving the Ship To Via list rejects an active option that does not map to one of those methods. Due time uses that method's hours. The order form hides the delivery method when return is See ShipTo and a ship-to line exists.
- `originals_source` is required on create. The choices are `Files attached below`, `Archived files at Accent Imaging`, `Send a vehicle to pick up originals`, and `Hardcopy or digital media provided`. Files attached below requires at least one uploaded file, and the order form shows the upload area only for that choice. Sending a vehicle is an inbound pickup of originals. It is not a delivery method and does not change Will Call, UPS, or Accent Truck. Orders created before the column existed have a null value and display as `Not specified` on the order, the work order, the admin board, search, and the print sheet.
- The company address is stored on the customer user (`address_line1`, `address_line2`, `city`, `state`, `zip`) and copied onto the order at submission. The order keeps that snapshot if the profile changes later. Customer users prefill the order form from the profile returned by login and `GET /api/auth/me`. Admins edit the profile address on Users and on Customers (`PUT /api/customers/:id`). That write is activity `user.updated` with the message `Updated address for {username}` and does not put the street into the activity summary. Older orders leave the address columns null and show blanks.
- `POST /api/uploads` accepts multipart field `files` for signed-in users. Allowed types are pdf, images, dwg, zip, and plt. Size is capped by `MAX_UPLOAD_MB` (default 25). Files are stored with a random filename. The folder is the File storage value in system settings when an admin has saved one, otherwise `UPLOAD_DIR`, otherwise `../data/uploads` resolved from the backend folder, outside the frontend web root. `GET /api/uploads/:id/download` and `DELETE /api/uploads/:id` require auth. Customers can access only their own files, and they can delete a file only while it is not attached to an order. Each user can leave at most `MAX_UNATTACHED_UPLOADS` files unattached (default 30). An unref'd sweep deletes unattached uploads older than `UPLOAD_ORPHAN_HOURS` (default 24). No confirmation email is sent; the API reports `confirmation.email_status` of `disabled`.
- File storage is an admin section on System Settings. It shows the absolute folder and how much free space it has. The folder may be a local path, a mapped drive such as `Z:\launchpad`, or a network share such as `\\server\share\launchpad`. A relative path, or a path inside `backend` or `frontend`, is rejected. So are `/proc`, `/sys`, `/dev`, a Windows device path (`\\?\` or `\\.`), any Windows admin share such as `\\server\C$` (including `\\MYPC\C$` and an IPv6 host), and the Windows directory. Saving creates only the final folder, and only when its parent already exists, then writes, reads, and deletes a test file. That check runs with a timeout so a stuck path cannot freeze the server. A folder under `/tmp`, or inside this repository, is allowed and shows a warning. The shipped `data/uploads` folder does not show the inside-project warning. The value is `system_settings.file_storage_dir`. Saving also writes `.launchpad-storage` in that folder and keeps the same id in `system_settings`. On first start, when no folder is saved, Launchpad creates `data/uploads` once if no marker has been recorded for it, then writes the marker. That includes a fresh clone with no `data` directory: only this shipped default creates the `data` parent. `UPLOAD_DIR=../data/uploads`, the value in `.env.example`, is that same default and is created the same way. After that marker is recorded, a deleted default folder is not created again. An `UPLOAD_DIR` that already exists is marked on first start even when the folder is empty, so the first upload works. A missing `UPLOAD_DIR` that points somewhere else is not created, and a saved folder is created only when an admin saves it. Restoring this database onto other disks means saving the folder again so the marker id matches that copy. If the marker is missing or does not match, or the folder itself is gone, uploads, downloads, and Move return HTTP 503 and the page shows a warning. A missing file inside a healthy folder is still HTTP 404. The process stays up and does not recreate the folder. New uploads, shared files, proofs, and inbound email attachments record that folder on the row. Older rows with no folder still open from the original `UPLOAD_DIR` or default location. A stored folder is used only when it is the current folder, `UPLOAD_DIR`, the default folder, or a folder saved before (those paths are kept in `file_storage_roots`). Move existing files copies each file, checks the size and a checksum, updates the row inside a transaction, and deletes the original only after that. Move also removes leftover `.moving-` files in the current folder when it starts. Run Move before you remove `UPLOAD_DIR`, or files that still have no folder recorded stop opening from that old location. It is safe to run again if it was interrupted. A second Move while one is already running returns HTTP 409. Bytes go through the local folder storage driver. `backend/storage/README.md` describes that driver and the place a OneDrive or SharePoint driver would be added. That cloud driver is not built. `node scripts/verify-phase19.js` checks the folder, the move, a deleted folder that must not be recreated, a fresh install with no `data` directory (including `UPLOAD_DIR=../data/uploads`), and a rejected `/proc` path.
- Customers sign in to the Customer Order Form (`/order`). That shell includes the notification bell. Staff land on the Dashboard. `node scripts/verify-phase1.js` from `backend/` checks migrations, roles, order numbers, concurrent creates, validation, uploads, and customer isolation.

Dashboard (admin, manager, and operator):
- Staff home is the Dashboard at `/`. Customers stay on the order form and receive HTTP 403 from `/api/admin-board`.
- `GET /api/admin-board` returns department tabs and queue counts, stat cards, recent activity, the last 10 barcode scans, pending approvals, and system alerts. `GET /api/admin-board/work-orders` returns one page of the active table (`limit` default 8, max 100, plus `offset`). It filters by `department`, `q`, `status`, `priority`, `due_from`, and `due_to`. `sort` is `arrived`, `due`, `order_number`, `company`, or `department`. With no sort, the list is date due ascending. A Complete login with no sort stays newest first.
- A staff user with `users.department` set sees only active work orders in that department. The table, stat counts, and department queue use that department. The board shows `Showing: {department}`. Recent Activity and pending approvals for that view are work orders whose current department, or the event's from or to department, is theirs. User and system events, such as creating an operator, are left out. Operators cannot widen it with `department` or `scope`. An admin with a department starts there and can pass `scope=all` to see every department again, including the full activity and approval lists. A manager has no department, so that board is already every department and does not show the department chip. A null department still shows the full board and keeps the department filter. A login whose department is Complete has no active queue, so that board defaults to work orders completed this month, newest first, and the chip reads `Showing: Complete · completed this month`. `node scripts/verify-phase8.js` checks the migration, the user department, that restriction, activity and approvals, the Complete default, department rename, the department scan, and customer isolation. A restricted activity query treats a non-JSON `activity_log.detail` as empty instead of failing the board.
- Active work is not finished (`completed` or legacy `complete`) and is not in the Complete department. On-hold work stays in the active queue. The Complete tab is finished work plus anything sitting in Complete. "Completed this month" uses `updated_at`, or `created_at` when that is empty, inside the current month in `DELIVERY_TIMEZONE`.
- The monitor columns follow the Launch Pad 2.0 order monitor. XFer Id/From stacks the work order number, company, and contact. To is the department name in a pill coloured with that department's colour, with the delivery method under it. Arrived, Retrieved, and Date Due stack the date over the time. Retrieved is the first barcode scan, or the first production-history row that is not the Order Created line, and reads n/a until then. Date Due sorts ascending by default. Process shows LiveOrder for open and in-progress work (On Hold, Complete, or Cancelled otherwise) and, under that, file count and total size such as `1 / 10 MB` or `0 / 0`. Size uses KB, MB, or GB. The count includes files on the work order and order-level uploads on its order. `process` on the payload is still the service name, then the production stage, then the department. Company and contact come from the order, then the customer.
- Each active-board row carries `urgency` for the shop timezone (`DELIVERY_TIMEZONE`; the code default is still UTC, and `backend/.env.example` sets `America/New_York`). The board categories are Overdue, New, and In Production. Overdue is open or in-progress work whose due time has passed, using the same clock rules as the delivery list. A date with no clock is overdue on a past shop day. New is still open and not overdue. In Production is in progress and not overdue. Due today and due soon are not categories. On-hold and finished work are not marked overdue. Rush stays the work order priority and is not a category. Overdue rows use a red-to-orange-to-yellow gradient. New rows are bold pale yellow. In Production rows use one light blue tint. Other rows alternate white and pale lavender. The legend, the row chip, the category filter, and the category stat cards each list those three names once. `node scripts/verify-phase14.js` checks the flags, the monitor fields, department scope, a manager move, and customer isolation. `node scripts/verify-phase16.js` checks the category filter, the print move, and the file size.
- The board opens on Active, which is every active job the viewer is allowed to see. All stays the same active total. Department tabs still come from `show_on_board` in `sort_order`. Search is a tab with the search box. An operator's summary is still only their department; Search and Active on that screen stay inside that department.
- Selecting a row fills the side panel. With nothing selected, the panel says "Select a transfer for more info about it." The panel shows company, contact, due time, originals, payment, project, delivery, line items, special instructions, production history, and recent activity. Print and Edit open the existing pages. Move to… stays on the board and is still admin and manager only. Options, above the table, holds the status, priority, and due filters, and a switch for the stat cards.
- The board reloads when the window regains focus, when a scan asks it to, and about every 60 seconds while the tab is visible. That reload does not move focus and does not clear the table. No Launch Pad 2.0 refresh interval was stored in this repo, so 60 seconds is the shop-monitor interval used here.

Printable work orders:
- `GET /api/workorders/:id/print` returns one work order. `GET /api/orders/:id/print` returns every work order on that order. Both require a signed-in user. Admin and operator can print any work order. A customer can print only their own orders and work orders. Someone else's id returns HTTP 404, the same as the other customer reads. No token returns 401. An admin, manager, or operator printing a job that is still `open` moves it to `in-progress`, writes one `Printed` production-history row, and writes `work_order.printed`. That update runs inside the print transaction and only when the row is still `open`, so a reprint or several prints at once add one row. A customer print does not move the job. Completed, on-hold, and cancelled jobs stay where they are.
- The payload is built from the order, its line items, attached file names, delivery, routing, and `production_history`. It includes contact, the snapshotted company address, project, originals source, payment method, return, Bill To when present, the delivery or will-call method, due date and time, priority, the delivery timezone, service and process, the service's own line fields, and special instructions. `due_time` is the order's due time, or the time on `work_orders.due_date` when the order has none. `timezone_label` is the short name for that due instant in `DELIVERY_TIMEZONE`, such as EST or EDT for `America/New_York`. `overdue` is true when that wall-clock due time has passed and the work order is still active (`open` or `in-progress`). Completed, on-hold, and cancelled work orders are not overdue. `due_soon` uses the same window as the delivery list. A line with no service fields still prints size, quantity, media, color, binding, mounting, lamination, and finishing. Mounting and lamination print as Yes/No when the line has no mount or laminate field. A null originals source or payment method prints as `Not specified`. A blank finishing value prints as `Finishing: None`. An order with no project name still prints. It does not include password hashes, card numbers, or stored upload filenames. A customer history row is department, status, and time. Staff also receive who recorded the step and the history note.
- The shop letterhead comes from System Settings (`company_name`, `company_address`, `company_phone`). When a key is missing, the sheet uses Accent Imaging, Inc., 8121 Brownleigh Drive, Raleigh, NC 27617, 919-782-3332. The hours label follows the order's method: Will Call (and a stored Customer Pickup) uses the Will Call window, and every other method uses the delivery window, including `DELIVERY_SLOT_MINUTES`. A UPS account number is printed only when the order has one.

The value must be 1 to 80 printable ASCII characters. `POST` and `PUT /api/workorders` reject any other `external_id` with HTTP 400. A blank `external_id` is still allowed. An older unprintable id already in the database prints as "barcode unavailable" and does not fail the rest of the order. Scanning the number with `POST /api/barcode` resolves that work order. The print view draws the SVG through an image so the work order number is not treated as page markup.

The sheet is a production ticket: navy header with the logo (no white plate), WORK ORDER, the work order number, and the Code 128 image on a white plate with a quiet zone and the number printed under the bars. Due date and time and the delivery method are prominent. Section headers are navy with a thin orange accent. Each work order ends with a blank write-in grid: Code (18%), Unit (12%), Quantity (22%), Description (33%), and Price (15%), with six empty rows about 0.45in tall. The grid header is navy with white bold uppercase labels and a thin orange accent. Cell borders are navy and grey so they stay visible in black and white, and the header prints with `print-color-adjust: exact`. The footer uses the system-settings letterhead, a print timestamp, and a page number. Page margins are 0.45in. A Rush priority prints RUSH. A passed due time prints OVERDUE only while the work order is active. Order date and history times use the shop timezone, the same way the Printed stamp does. A ticket may use two letter pages. Pages after the first of a work order repeat the work order number and customer. Panels, history rows, and the write-in grid stay together. Those words stay on the page when color is not printed. The toolbar has Print and Download PDF. Download PDF opens the browser print dialog. `@media print` hides the toolbar. There is no server-side PDF.

Print, Move to… (admin and manager), and Edit (admin, manager, and operator) stay on the header. The Routing tab still lists production history and activity, including the Manual marker.

Admin configuration:
- Services (`/services`, `/api/services`) list, create, edit, and deactivate a service. Fields are name, code, suffix mode (`sequence` or `code`), department, default turnaround hours, sort order, and active. A deactivated service leaves the customer order form. Existing orders keep their work orders. Seeded services stay on sequence suffixes (`-A`, `-B`, `-C`). Code mode uses the service code as the suffix. The department must be an active department. Admins edit a service's line-item fields at `GET` and `PUT /api/services/:id/fields`. Operators and customers receive HTTP 403. A save replaces the set by key: an omitted key is deactivated, not deleted, so older orders can still show its label. Select options stay on the field when they are marked inactive. The change writes `service.fields_updated` in the same transaction. Init inserts a missing seed key and does not overwrite a label or option list an admin already saved. Changing a field key leaves older values under the previous key.
- Users (`/users`, `/api/users`) list, create, edit, and deactivate staff and customer accounts, and change role. Admin and operator accounts can store a department. Blank means every department, and the Users page offers that as All departments. A manager cannot store one: the field is hidden, and the server clears it. The name must match a row in the departments table. A name that is only a legacy board label, such as Manufacturing or Assembly, is rejected, and the error lists the valid department names. Customers are not assigned one. Login and `GET /api/auth/me` return `department`. Creating or changing it writes the activity log. Renaming a department with `PUT /api/departments/:id` runs in one transaction. It updates the live name on `users.department`, `work_orders.department`, `work_orders.next_department`, `services.department_name`, `departments.next_department`, and `barcode_locations.department_name`. A scan location is renamed only when its name is still the department name. A location an admin renamed stays as saved. `work_orders.assigned_department_id` is the department id, so it already follows. Production history, barcode event from/to and location, activity detail, notification text, alert text, production-board lanes, routing notes, and system settings are left as written. There is no department name in system settings, and the stage map is the `BARCODE_LOCATION_STAGES` environment value. The activity row is one `department.updated` and its `changes` object counts the rows updated in `users`, `work_orders`, `services`, `departments` (route targets), and `barcode_locations`. A route target that moved is marked updated so a later init does not put the old name back. Work orders match the previous name after trimming and ignoring case. Users, services, department routes, and scan locations still match exactly, so a different casing of those is left alone. Creating or saving a work order stores `departments.name` when the text matches a department that way. A name that is not in the table is stored trimmed. Creating or renaming onto a name that matches another department except for case returns HTTP 409. Quality, Dispatch, and Complete cannot be renamed, including a change of case only. That request returns HTTP 400 and explains that the department is a system department. The complete queue and the Quality and Dispatch scan stages still use those names, so the rename is rejected instead of leaving those checks pointed at a name that no longer exists. Omitting description, color, icon, sort order, active, or show on board on the update leaves the stored value. An empty string clears a text field. Init adds `idx_departments_name_nocase` when no case-only duplicates already exist, and otherwise warns and leaves those rows in place. `node scripts/verify-phase9.js` checks the cascade, a location-name conflict that rolls the transaction back, the restricted board and scan after the rename, the 409, a non-JSON activity detail, the one-time department seed, the system-department rename, a name-only update, canonical work-order departments, and the board tab after a rename. Responses never include password hashes. `POST /api/users/:id/password` uses the same reset helper as the customer password route and returns a generated password once. An admin cannot demote or deactivate their own account, or the last active administrator. A role change or deactivation clears that user's sessions. An inactive user cannot sign in. Lists are paginated and sort columns are whitelisted.
- System Settings (`/settings`, `/api/settings`) store the company letterhead, due-soon hours, `last_backup_at`, whether customers are emailed when files are shared, and the file storage folder. Cutoffs, timezone, Will Call hours, delivery hours, and upload limits are shown from the environment and are not writable here. Every stored value is validated on the server. Clearing due-soon hours returns delivery timing to `DUE_SOON_HOURS`. The printable work order reads the letterhead from these settings. Admins can send a test email from this page when SMTP is configured. File storage shows the current absolute folder, its free space, a warning when that folder is under `/tmp` or inside the project (the shipped default folder does not show the inside-project warning), and a warning when the folder cannot be reached. `PUT /api/settings/file-storage` with `{ "path" }` checks the folder before saving. An empty path follows `UPLOAD_DIR` again. An `UPLOAD_DIR` that already exists is marked on first start even when it is empty. A missing `UPLOAD_DIR` is not created, except when it is the shipped `../data/uploads` path: that one is created once, including the `data` folder on a fresh clone. Restoring the database onto other storage requires saving the folder again so the marker matches. `POST /api/settings/file-storage/move` copies existing files into the current folder. Run that Move before removing `UPLOAD_DIR`.
- Notification settings are on the Notifications page for admins (`GET` and `PUT /api/notifications/settings`). In-app events start enabled and can be turned off. Email rows stay locked off. Enabling one returns HTTP 400 with "Email notifications stay off. No mail is sent."
- Activity Log (`/activity-log`, `/api/activity`) filters by date, user, and action type, searches, pages, and accepts `format=csv`. Each admin change to a service, user, setting, notification preference, or barcode location writes an activity row in the same transaction as the change.
- Barcode Settings (`/barcode-settings`, `/api/barcode/locations`) add, edit, and remove locations. A location needs a department, a stage, or both, and those names must already exist. `POST /api/barcode/dry-run` resolves a typed scan without writing a scan, a department move, or activity. The result links to the printable work order. Operators may read the location list for the scan page. They cannot change locations or run the dry run.
- Search Orders (`/search`, `GET /api/search/orders`) is available to admin and operator. Filters are order number, work order number, company, contact, phone, email, status, created-date range, and service. The text query also matches payment method and line-item field values. Results are paginated and include payment and a line-detail summary. Sort columns are whitelisted. Each row links to the order, the work order, and the print view. The deliveries CSV includes payment method and bill-to company. A cell that starts with `=`, `+`, `-`, or `@` is prefixed with a single quote.
- The Reports sidebar entry expands to the existing report pages. Customers receive HTTP 403 on these admin APIs. Operators receive HTTP 403 on services, users, settings, activity, notification settings, and barcode writes. `node scripts/verify-phase4.js` checks roles, validation, last-admin protection, settings, activity writes, search, and the barcode dry run. `node scripts/verify-phase5.js` checks service-field validation, the admin field editor, payment, Bill To, legacy rows, and concurrent saves. `node scripts/verify-phase6.js` checks the Small Format catalog on a fresh database and on one that already has the previous seed. `node scripts/verify-phase7.js` checks fresh and upgraded scan locations, including a legacy Quality Control scan and an admin-customised location.

Reports (admin and operator):

Files from Accent:
- Staff (admin, manager, operator) send proofs and finished files to a customer from the order and from a work order. `POST /api/orders/:id/shared-files` accepts multipart field `files`, an optional `message`, and an optional `work_order_id` that must belong to that order. The same size, type, and name rules as `POST /api/uploads` apply (`MAX_UPLOAD_MB`, `MAX_UPLOAD_FILES`, `UPLOAD_DIR`). Names are sanitized, the stored name is random, and a path is not accepted as a filename. `GET /api/orders/:id/shared-files` lists them. Pass `work_order_id` to include files for that work order and files shared with the whole order. `GET /api/shared-files/:id/download` requires a signed-in user. `DELETE /api/shared-files/:id` and `POST /api/shared-files/:id/replace` are staff-only and soft-delete the previous row. The activity log records the send, delete, replace, and each customer download.
- A customer can list and download files only on their own orders. Another customer's id, a guessed file id, a removed file, and a file missing from disk are HTTP 404. A missing file does not set `customer_downloaded_at`. A customer who tries to upload, delete, or replace receives HTTP 403. The first customer download sets `customer_downloaded_at`. Staff downloads do not. Staff on the order page and the work order page see "Downloaded by customer" with that time in `DELIVERY_TIMEZONE`, or "Not downloaded by the customer". Customers do not see "Not downloaded by the customer".
- Sharing writes an in-app notification for that customer, "New files for order {order number}", unless the Files from Accent event is turned off on the Notifications page. The bell opens `/orders/:id`.
- Email is optional on each send. The checkbox defaults from `system_settings.email_customers_on_file_share`, which init inserts as on only when the key is missing. Staff can change the recipient (default is the order contact email) and add up to five CC addresses before sending. Addresses are validated and header characters are rejected before anything is stored. File-share and test emails share a limit of `EMAIL_RATE_LIMIT_MAX` per `EMAIL_RATE_LIMIT_WINDOW_MS` (default 30 per 15 minutes) for each signed-in user. Over that limit, the files are still shared and `email.status` is `rate_limited`. `POST /api/settings/test-email` still returns HTTP 429. The message is a short HTML page plus plain text. It uses the letterhead already stored in system settings and a link to sign in and open the order (`PUBLIC_APP_URL/login?next=/orders/:id`). There is no public download link. User text is escaped. Success or failure is written to the activity log once per recipient.
- SMTP comes from `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM`, and `SMTP_SECURE`. Those values stay in the environment and are not committed. `SMTP_TIMEOUT_MS` sets the connection, greeting, and socket timeouts (default 12000, between 1000 and 120000). An unreachable host returns HTTP 201 with `email.status` `failed` instead of waiting on the nodemailer default. When `SMTP_HOST` or `SMTP_FROM` is missing, the files are still shared, the API returns `email.status` of `not_configured`, and the page says email is not set up. `POST /api/settings/test-email` is admin-only and returns the same not-set-up error without sending. `MAIL_TRANSPORT=json` or `stream` is only for tests (`NODE_ENV=test`) and selects a nodemailer mock. Send Proof:
- Staff (admin, manager, operator) send a proof from Send Proof in the sidebar, or from an order or work order. `POST /api/orders/:id/proofs` accepts multipart field `files`, a required `message`, and an optional `work_order_id` that must belong to that order. The same size, type, and name rules as `POST /api/uploads` apply. Names are sanitized and the stored name is random. Versions are v1, v2, and so on, counted separately for the whole order and for each work order. A new version is rejected with HTTP 409 while the latest version in that scope is still awaiting approval. `GET /api/orders/:id/proofs` lists them. `GET /api/proof-files/:id/download` and `GET /api/proof-files/:id/view` require a signed-in user. Download uses an attachment disposition. View uses inline. Both send `X-Content-Type-Options: nosniff`, a content type from the extension, and `Cache-Control: private, no-store`.
- The owning customer sees the proof on the order and under Proofs in the sidebar, which lists proofs still awaiting approval. They can view and download, then `POST /api/proofs/:id/approve` or `POST /api/proofs/:id/changes` with a required `comment`. The decision stores who decided and when. A second decision on that version is HTTP 409. Another customer, a guessed id, and a missing file are HTTP 404. Staff who try to decide, and a customer who tries to send, receive HTTP 403.
- The work order's `proof_status` follows every proof that covers that job: the latest version for that work order, and the latest version for the whole order. Labels are Awaiting proof approval, Changes requested, and Approved. Awaiting wins when any latest version is still awaiting, then Changes requested, then Approved only when every covering series is approved. Staff see that chip on the work order and on the board detail panel, with the customer's comments. While any covering series is awaiting or changes were requested, a staff print does not move the job from open to In Production and does not write the Printed history or activity row. Approving one series leaves the job open when another series is still awaiting, and that older proof can still be approved. Approval of the last open series sets the status to Approved and, in the same transaction, moves each affected open job to In Production. That update is conditional (`status = 'open'`), so two approvals at once produce one production-history row and one `work_order.proof_released` activity row per job. A job that is already In Production, on hold, or complete stays as it is. A newer proof on a job that is already In Production shows that the job is already In Production.
- The customer gets an in-app notification, "New proof for order {number}", unless Proof ready is turned off. A decision notifies staff ("Proof approved" or "Changes requested") and does not appear in the customer's list. Changes requested also emails active staff who have an email address when SMTP is configured. The customer email is optional on each send and defaults from `system_settings.email_customers_on_proof` (on when the key is missing). It reuses the file-share mailer: the same address checks, rate limit, timeouts, and a sign-in link (`PUBLIC_APP_URL/login?next=/orders/:id#proofs`). There is no public download. If email is not set up, the proof is still saved. `node scripts/verify-phase17.js` checks roles, isolation, versions, the print hold, and a double approve.

Email orders:
- Staff with the admin, manager, or operator role open Email Orders in the sidebar (`/email-orders`). A customer receives HTTP 403 on `/api/inbound-emails` and never sees the page. The mailbox is read with Microsoft Graph application permission `Mail.Read`. Launchpad does not mark messages read, move them, or delete them.
- The server reads `M365_TENANT_ID`, `M365_CLIENT_ID`, `M365_CLIENT_SECRET`, `M365_MAILBOX`, and optional `M365_POLL_SECONDS` (default 180) and `M365_FOLDER` (default Inbox) from the environment. The client secret is not stored in the database and is not written to the log. If any of the four required values is missing, polling stays off. `M365_LOGIN_BASE_URL` and `M365_GRAPH_BASE_URL` override the Microsoft hosts for tests. Leave them unset in production.
- A Microsoft 365 administrator registers this in Entra ID. Create an app registration, add a client secret, and grant the application permission Microsoft Graph `Mail.Read` (not a delegated permission, and not `Mail.ReadWrite`). Grant admin consent. The Graph permission is tenant-wide until Exchange restricts it, so the administrator then limits the app to the one orders mailbox. Either of these is enough. Application Access Policy: create a mail-enabled security group that contains only that mailbox, then in Exchange Online PowerShell run `New-ApplicationAccessPolicy -AppId <application-id> -PolicyScopeGroupId <group> -AccessRight RestrictAccess -Description "Launchpad orders mailbox"`, and confirm with `Test-ApplicationAccessPolicy -Identity <orders mailbox> -AppId <application-id>`. A mailbox outside the group should be denied. RBAC for Applications is the newer Exchange alternative: create the app's service principal in Exchange and assign the application `Mail.Read` role with a management scope of that one mailbox, not the whole organization.
- The poller uses a delta query on the folder, or the saved `receivedDateTime` watermark when the delta link is reset. The first run imports only mail received after it starts. Older mail already in the mailbox is left there and is not imported. Each new message is stored once, keyed by the Graph message id. The subject is stored as plain text. The body is stored as text with HTML removed. Attachments use the same type and size rules as order uploads. A file that is not allowed is recorded with a reason and is not saved. A draft suggestion matches the sender to one active customer by email, or by domain when exactly one customer uses that domain, and picks a due date, quantity, job description, and PO number from the subject and body when those phrases are present. The draft is editable. It is not an order.
- Opening an email shows the message, the attachments, and the order form filled from that draft. Submitting uses the same order validation as Create Order. The saved attachments are copied onto the order as order files. The email is marked Converted and links to the order. Dismiss marks it Dismissed and does not create an order. Two converts at the same time create one order. System Settings has Poll the orders mailbox. When that switch is off, the schedule does not run. Check now, on System Settings and on Email Orders, is admin-only and still reads the mailbox. The last check time and any error are shown there. `node scripts/verify-phase18.js` checks the token, polling, dedupe, attachments, rejected file types, conversion, a double convert, roles, and a subject and body that contain a script tag.

Notifications:
- `notifications` stores one row per event. `notification_reads` stores who has read it. Both are created by `database/schema.sql` and again by `init_db.js`, so an existing database can be updated by running init again.
- Events are: a delivery becoming overdue, a delivery due within `DELIVERY_DUE_SOON_MINUTES` (default 60), a work order put on hold, a work order completed, and a rush-priority work order created. Rush is only notified when the work order is created, not when priority is changed later. On-hold and completed notify on the transition into that status. When `DELIVERY_DUE_SOON_MINUTES` is unset, that window follows `DUE_SOON_HOURS` (default 1 hour), so the delivery list and the notification use the same due-soon period.
- The same delivery and due time are not notified twice. A changed due time can notify again. A scheduler (`setInterval`, unref'd) runs the delivery check every `NOTIFICATION_CHECK_INTERVAL_SECONDS` (default 60) and once at startup.
- `GET /api/notifications` returns `{ notifications, unread_count, total, limit, offset }`. Admin and manager see every notification. An operator sees every notification except quote requests. A customer sees only rows whose `customer_id` is their user id.
- `POST /api/notifications/:id/read` and `POST /api/notifications/read-all` mark the signed-in user's visible notifications. A customer cannot mark another customer's notification.
- The top bar has a bell with an unread badge. It polls about every 45 seconds and opens a short list. The customer order form shell shows the same bell. `/notifications` is the full list for every role. Admins on that page can turn individual in-app events off. Those disabled types are skipped when notifications are written. Email rows on the same page stay off.
- Email for these notification events is off unless `EMAIL_NOTIFICATIONS` is true. Even then that interface is a stub: it does not read SMTP settings and does not send email. Mail for files shared with a customer is separate and uses the SMTP settings above.

Ready for pickup:
- Order status is `In Production` until an admin, manager, or operator sets `Ready for Pickup` with `PUT /api/orders/:id/status`. A customer can see the status and cannot change it. Work order statuses and delivery statuses are unchanged. The control is on the order page and on a work order that belongs to an order.
- The first time an order enters Ready for Pickup, Launchpad emails the order contact (or the account email) and, when the customer has opted in, texts their mobile number. The email uses the customer template, including the Accent Imaging and Accent Corporate Graphics credit, and names the order number and the order's shop location (name, address, and phone from Locations). The text is short: order number, location name, address, and phone. A repeated save of the same status does not send again. Leaving Ready for Pickup and setting it again sends once more. `orders.pickup_email_sent_at` and `orders.pickup_sms_sent_at` record a successful email and a sent or dry-run text. A mail or text failure is logged and does not undo the status change.
- Customers set a mobile number and the SMS opt-in on Place an order. The checkbox is off until they agree, with the wording "I agree to receive order status texts from Accent Corporate Graphics. Msg & data rates may apply. Reply STOP to opt out." Opt-in without a number is rejected. A 10-digit number is stored as US E.164 (`+1` plus those digits). Only the customer can turn texts on. Admins and managers can see the number and the opt-in, change the number, and turn texts off. The Users page does the same for a customer and clears both when the role is not customer. A customer who is not opted in, or whose number is not a valid mobile number, is not texted. The email still goes out.
- Search Orders can filter by Ready for Pickup, which matches the order status. The home dashboard counts those orders for the shops the signed-in user can see. The production board shows a Ready for Pickup chip on a job whose order is ready, and the same location limit. A scan shows that order status. Staff who can change an order status can mark it Ready for Pickup from the scan page and the header scan. An operator at another shop gets HTTP 404.
- Texts use the Twilio Messages API (`TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_FROM_NUMBER`). When any of those is missing, the text is written to the server log as `SMS dry-run:` and is not sent. `TWILIO_API_BASE` overrides the Twilio host only when `NODE_ENV=test`. `node scripts/verify-pickup.js` checks the dry-run, opt-out, a repeated save, and a Twilio failure that still marks the order ready. `npm run verify:phase1-19` runs it.
